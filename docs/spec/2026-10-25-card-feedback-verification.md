## 实现边界

- 仅原提问者的反馈有效；以 Stream 回调业务载荷中的员工 `userId`（`userIdType=1`）和服务端保存的提问者绑定比较，不信任按钮额外参数中的身份声明。
- 每张卡片以账号及 outTrackId 精确定位，不回退到会话最近回答。
- 当前状态为 `none / like / dislike`，切换和撤销替换当前状态；操作历史与统计口径分开。
- 正常完成后才允许评价。停止、失败、模型认证错误、主动通知和无法关联的旧卡片不补建评价归属。
- 成功记录后才返回当前操作者的私有 UI 数据，不更新其他成员的选择，不调用模型或学习模块。
- 本地每卡一个原子文件，先写临时文件并 fsync 后 rename，按卡片串行处理。保存失败不 ACK，保留平台重试机会；回调 ID 去重并拒绝早于当前状态的事件。
- 原提问者可以在私聊查询本人统计，以及按卡片 ID 精确反查原问答；仅查询详情时读取相应转录，旧记录不补猜。管理员导出沿用本地文件权限，无新增公网接口或常驻进程。

## 原生模板协议的真实发现

默认 Action ID `sys_action_like_component` 在本轮环境中仅表现为平台状态变化，没有捕获到对应业务 Stream 事件。将原生 Feedback 的 Action ID 改为 `feedback_vote` 后，官方 SDK 立即捕获到真实回调；此后在插件自身的 Stream 回调路径完成了保存与界面回写验证。

真实载荷的脱敏结构：

```json
{
  "type": "actionCallback",
  "userIdType": 1,
  "userId": "owner-user-id",
  "outTrackId": "card-example",
  "content": "{\"cardPrivateData\":{\"actionIds\":[\"feedback_vote\"],\"params\":{\"variableKey\":\"node_ocmncu094ga_likeOrDislike\",\"variableValue\":\"like\",\"extraParams\":{}}}}"
}
```

- 赞踩状态字段：`<componentId>_likeOrDislike`；值为 `like`、`dislike`、`none`。
- 原因字段：`<componentId>_dislikeTags`；原因是字符串代码数组，例如 `["2","3"]`。
- 回调响应使用 `cardUpdateOptions.updatePrivateDataByKey=true` 与 `userPrivateData.cardParamMap`，保留其他私有字段。
- 原因尚未选择时，私有字段应返回 JSON 字符串 `"null"`。空数组 `"[]"` 表示用户已关闭面板而未选择原因；两者不能混用，否则首次点踩的原因面板不会展开。
- 真实模型认证错误也可能经宿主最终消息路径交付；必须检查最终 payload 的 `isError`，不能仅凭卡片结束状态计为正常回答。

回调响应结构可参照[钉钉官方 Stream SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-go/blob/main/card/model.go)。

## 真机结果

仅将可核对的真实交互记为通过。固定测试回答由真实模型生成，未以手工创建归属记录替代入站链路。

| 用例 | 证据与结果 |
| --- | --- |
| 正常 AI 回答 | F6 真实私聊入站，原消息与提问者绑定成功，模型正常回答后获得评价资格 |
| 点赞及撤销 | 客户端高亮与持久化 `like → none` 一致 |
| 点踩及原因提交 | `dislike` 保存成功，真实提交的 `2、3` 两项原因准确落盘 |
| 原因面板关闭 | 关闭后保留点踩，空原因数组与“尚未选择”状态明确区分 |
| 赞踩直接切换 | `dislike → like → dislike` 一致，旧原因清空，不累计两票 |
| 网关重启 | 重启后原点踩仍在；恢复默认连接管理模式后，继续撤销及提交原因成功 |
| 非提问者拒绝 | 成员 B 发起 G4，成员 A 点击被拒绝，B 的记录无新增票数或历史 |
| 群聊原提问者成功 | 成员 B 点击自己的 G4，成功保存一条点赞 |
| 不覆盖他人评价 | B 已点赞后，A 再次点击仍被拒绝，B 的点赞及事件数量保持不变 |
| 拒绝说明 | 最终构建以普通私聊消息说明原因，不生成带赞踩按钮的拒绝卡片 |
| 本人统计 | `/feedback stats 7d` 在钉钉显示当时 1 条有效回答、1 次点踩及两项原因，与实际文件一致 |
| 统计隔离与导出 | 后续 A 的本地导出仅包含 A 的两条正常回答，不包含 B 的点赞卡片；认证错误卡片被排除 |
| 错误回答过滤 | F3 的认证错误卡片没有 completedAt，未进入正常回答数 |

测试中曾临时使用已有的原生 SDK 连接模式定位消息分发；重启恢复、原因提交、群聊权限拒绝、原提问者成功和最终拒绝提示均在默认连接管理模式下复验。

另一个共用同一机器人应用的实例会接收部分消息。F1/F4/F5 及一次 `30d` 查询被该实例处理，其输出未作为本插件通过证据；遵照用户要求未改动该实例。成功的用例以本机卡片 ID、Stream 日志及持久化文件关联确认。
